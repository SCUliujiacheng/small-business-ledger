# 开始用自己的账本

适合的用法：老板或负责人在一台电脑上记销售、日常费用和收付款，月底核对经营情况。先用几天虚构数据熟悉流程，再决定是否适合自己的业务。暂时不要用它替代原来的票据和正式会计账。

## 1. 示例和真账分开

第一次启动默认是空账本，不需要载入示例。已载入示例的账本会一直显示“虚构数据”，不要往里面记真实交易。

如果已经试过示例，先关闭服务，用另一个数据库文件开始。Windows PowerShell 示例：

```powershell
$env:LEDGER_DB_PATH = 'data/my-shop.db'
.\scripts\start.ps1
```

每次启动都使用同一个文件路径；路径变了就是另一份账本。不要直接双击数据库文件，不要把运行中的数据库放到共享盘供多人同时打开。

## 2. 每天怎么记

1. **发生销售**：在“记一笔”填写项目、成交数量、单价和已售数量对应的单位直接成本。赊账时填客户和约定收款日。成本尚未付清时另填供应商和付款日。
2. **发生费用**：房租、人工等单独记费用，填写收款方。已经算进销售的直接成本不要再记一次费用。
3. **钱实际到账或付出**：在“欠款清单”或“收付款”登记。收一半就记一半；业务日期不等于实际收付日期。
4. **当天核对**：对照现金、微信/支付宝及银行流水查漏记。老板投入和取出资金单独登记，不算利润。
5. **留一份备份**：收工后在“导入与备份”下载当前完整 JSON，另外保存到安全的位置。备份包含客户和经营信息，不要发到公开位置。

收款日为空时，清单显示“未设到期日”，不会擅自判断逾期。销售同时产生一笔应收和一笔直接成本应付；如果一次销售对应多个成本收款方，本版不能逐个管理这些供应商欠款。

## 3. 看欠款时留意日期

“截至日期”是查账日期，不是只查当天：10 月 31 日清单包含此前发生、到这一天仍未结清的业务。11 月收的货款不会冲掉 10 月底的应收。

从历史清单登记收付款时，系统会再检查当前余额。后来已经结清的款不能再收一次。到期当天不叫逾期，没有约定日期的款也不叫逾期。

## 4. 保存时断网或报错

本机程序不依赖互联网，但后台关闭、浏览器中断也可能使页面没收到保存结果。如果页面提示结果尚未确认，保持原内容，用页面上的重试操作确认；同一次请求编号不会重复入账。

不要关闭页面后凭感觉再记一笔。关闭后重新打开的表单是新的操作，应先查看销售或流水清单。确认多记了，再作废错误记录并写明原因；作废不是退款。

## 5. 升级

1. 先下载并另存一份当前完整 JSON 备份，再停止账本服务。
2. 拉取新代码，执行 README 中的依赖安装和前端构建命令。
3. 使用原数据库路径启动。第一次打开旧版非空账本时，程序会先保存旧格式快照，再迁移结构。
4. 核对业务数、流水数和最近一笔交易。迁移失败时不要删库重来，保留原文件和错误信息。

数据库已升级后不要用旧代码直接打开。需要退回旧版时，使用升级前的版本 1 JSON 备份，恢复到旧版程序的新空账本。

## 6. 从备份找回

自动备份位于数据库旁的 `<数据库文件名>.backups` 文件夹，最近 30 份；每份是修改前的状态。因此最后一笔新增可能不在最近自动快照里，手动“生成当前快照”或下载完整 JSON 才包含当前全部已提交记录。

这个文件夹留给程序管理，不要存放其他资料或改成目录链接。程序只轮换名称和内容均符合备份格式的文件；损坏或无法识别的文件会留在原处，不列入页面清单，也不占用这 30 个名额。发现此类文件时先保留原件排查，不要只改名后尝试恢复。

恢复时不要覆盖原账本：

1. 先停止服务并保留现有数据库和备份文件夹。
2. 用新的文件名启动，例如 `$env:LEDGER_DB_PATH = 'data/recovered.db'`，再执行启动脚本。
3. 在“导入与备份”选择需要的 JSON，确认恢复。
4. 核对截止日期、业务数、流水数、未收未付及最近交易；有差异时保留两份数据继续排查，不要急着删除原文件。

备份目录无法写入或磁盘已满时，非空账本的修改会被阻止，原账不变。先腾出空间或修复目录权限，再原样重试。同盘备份不能防电脑丢失和硬盘损坏，至少再保留一份不同位置的备份。

## 什么时候不适合继续用

需要退款、订金、销售前付款、库存、多人权限、发票报税或期初应收应付导入时，应使用覆盖这些业务的工具，不要通过改日期、负数或作废绕过。本版最多保存 10,000 条业务与流水，作废也计数，导出不会释放容量。
